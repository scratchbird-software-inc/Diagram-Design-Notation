# 25. Diagram field guide and executable documentation

**Documentation edition: field-guide-0.7. Runtime: DDN 0.7.0.**

The field guide is the user-oriented counterpart to the language specification. A notation registry is not a tutorial, and a list of rendered files is not a diagram-type catalogue. The 0.7 edition is generated by `tools/build-field-guide.mjs` from the registry, the example corpus and `standard/submission/facts.json`, and lives at `field-guide/` (mirrored into the website under `guide/`).

## Required chapter contract

Every chapter supplies: a stable chapter ID; category and support level; the entry workspace and selected view; what the diagram shows; why and when it is useful; how to read the example; the input information to gather first; a live, source-editable rendering; a guided first edit executed at build time; an authoring walkthrough with the actual view declaration; explicit profile and projection identity; declared limits and common mistakes; and background references where applicable. Optional variants render alternate views of the same model; decision and lifecycle chapters add a bounded evaluation panel.

The live diagram MUST use the same public `DDNLive` distribution as the diagram tool (lesson pages load `ddn.global.js`, `ddn-graph.js`, `ddn-iso.js` and `ddn-geo.js`; a view declaring a geography receives the bundled world-110m GeoJSON inline). A guided edit MUST go through the public authoring/transaction API (label, record value, matrix cell, rule property, panel property or keyed data swap), MUST change the render, and MUST be undoable to the byte-identical shipped example — both SVG hashes are recorded in the chapter's evidence. Editing preserves contributing identities unless identity itself is intentionally edited.

Source files, format definitions and view references are shared. Each lesson loads its import closure; a chapter with variants renders each variant from the same closure. A variant view is not automatically a claim of semantic identity. The series, target and waterfall reconciliations in this edition use the actual records consumed by their charts.

## Inventory and support levels

The edition has 146 chapters (133 native, 13 technique). Across them they exercise 70 distinct installed profiles and all 12 projection kinds. These counts are generated into `field-guide/catalogue.json` at build time and describe this edition's curated coverage, not the number of all imaginable diagram types or an external-product parity score.

- **Native:** a directly implemented DDN capability within its declared limits.
- **Equivalent:** a constructive DDN teaching template for the same information; no external notation certification is implied. (No chapter in this edition currently needs this level.)
- **Subset:** an explicitly bounded implementation of a wider diagram family. (None currently.)
- **Technique:** layout, routing, detail, palette or publication choices; not an additional diagram type.
- **Unsupported/limited appendix:** a gap and the closest honest alternative, not a fake supported diagram. (None currently; gap candidates recorded in the project gap register, not in the guide.)

Chapter coverage is enumerated in `field-guide/catalogue.json`; profile/projection coverage is in `field-guide/coverage.json`. `field-guide/example-index.json` maps every chapter to its entry workspace, view and import closure. `field-guide/chapter-plan.json` records the full chapter map; every entry in it is delivered in this edition.

## Editing and file behavior

The reader can modify any definition through the chapter's source pane: labels, fields, values, relationships and format/view declarations. Applying source updates the live workspace and re-renders; an invalid draft is rejected with the diagnostic named, the previous output kept. Guided edits and source applications share one undo/redo stack; a reset control restores the shipped example. Chapters offer download of the current SVG and the current `.ddn` file. Because a single DDN file may not be self-contained, the source pane exposes every file of the import closure, so a reader downloading one file can see exactly which siblings it needs.

Decision chapters can evaluate the shipped table against one JSON input record, and lifecycle chapters can replay one event list through the flat machine; both are bounded local witnesses through the same workspace API, not execution of business actions.

The full diagram tool remains the richer environment for file renaming, creation/deletion, graphical pinning and workspace management. The field guide is an executable tutorial, not a second rendering implementation.

## Testing and regeneration

`node tools/build-field-guide.mjs` checks and renders every chapter fixture, executes and undoes every guided edit, records both SVG hashes, and rebuilds the HTML/Markdown/JSON guide including the portable edition. `npm run test:field-guide` runs two independent gates: `tests/field-guide.js` regenerates the whole guide into a temporary directory and byte-compares, audits the catalogue against `standard/submission/facts.json`, re-renders every fixture against its recorded hash, and checks page self-containment; `tests/field-guide-browser.js` drives real lesson pages and the portable edition in headless Chromium — guided edit, undo, variants, evaluation panels and hash routing.

Each source exercise has before/after SVG hashes; examples keep source IDs and dependency paths. Warnings are preserved.

The website mirrors the guide under `guide/` with a navigation entry, and the portable edition (`field-guide/portable.html`, mirrored at `guide/portable.html`) is a single self-contained file: minified runtimes, every chapter body and payload, and the deduplicated source closure are inlined; chapters are addressable by URL hash. It has no external runtime/CSS/font/source/image requirement. Only the active chapter's diagram is mounted, rather than hundreds of hidden diagrams.

## Boundaries

A successful documentation fixture is not professional approval, a proof of globally optimal layout, deployed accounting/security behavior, or external standard conformance. Current browser/CSP/accessibility/font qualification and the prior production assurance gates remain separate. No confidential source should be delivered to a public viewer merely to hide it using presentation settings.
