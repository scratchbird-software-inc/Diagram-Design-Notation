## Logical relational schema

*Data structures and meaning · native · `website/examples/use-cases/03-relational.ddn` # `diagram` · ddn@1*

**What:** Tables and references at design level: keys, cardinalities and which table owns a fact — still no storage engine decisions.
**Why:** Move from business nouns to a checkable structure: every relationship now has a home and a direction.
**When:** After the conceptual ER pass, before physical naming, indexing and platform choices.

**Read it:** Each box is a table; read keys first, then the reference arrows from foreign key to primary key. Crow's-foot marks state how many children a parent may have — claims, not constraints enforced here.
**Gather first:** The entity list from the conceptual model; Candidate keys per table; Ownership rules for every relationship

**Pitfalls:** Do not put a foreign key on both sides. A many-to-many without a join table hides a missing entity.
**Limits:** Logical only: datatypes, indexes and platform types are declared in the physical model, not here.

**Guided first edit:** Only the label of Customer / review changes; keys, references and every identity are untouched. (evidence: render changes, undo restores shipped bytes: true)

## Physical representation and datatype documentation

**What:** SQL objects with their dependencies: which view reads which table, which table feeds which report.
**Why:** Know the blast radius of a schema change before you make it.
**When:** Impact analysis before renaming, splitting or dropping database objects.

## Document and embedded-object schema

*Data structures and meaning · native · `website/examples/use-cases/05-documents.ddn` # `diagram` · ddn@1*

**What:** A document model: nested objects, arrays and embedded structures with their containment rules.
**Why:** Tree-shaped data needs its own contract — tables of one row type do not describe nesting.
**When:** Designing JSON documents, message payloads, or any hierarchical record.

**Read it:** Containment reads top-down: each level owns the fields below it. Arrays are plural by contract, not by current length.
**Gather first:** The nesting levels; Which fields are arrays; Required-versus-optional per node

**Pitfalls:** Do not flatten a tree into parallel tables just because it feels relational. An optional node with required children is usually a modeling mistake.
**Limits:** Structural contract only; no validation engine runs against live documents.

## Text fit — wrap, grow, shrink and honest overflow

*Techniques · technique · `field-guide/sources/text-fit.ddn` # `fitted` · ddn@1*

**What:** How boxes adapt to their text: wrap fixes the width and grows downward, grow expands both axes to declared bounds, and shrink steps the font down to a floor.
**Why:** Hand-tuning box sizes against text that keeps changing is the chore text_fit removes — with bounds and diagnostics so adaptation stays honest instead of silently clipping.
**When:** Long labels, generated text, multilingual content — anywhere text length is not under the author's full control.

**Read it:** The renderer measures, resizes and re-lays-out in at most two passes; whatever still overflows after that is a residual overflow and is reported. Residual overflow fires DDN-LW07 (wrap/grow) or DDN-LW08 (shrink at its floor) at render time, naming the element, the overflow and the remedy — check stays clean because it never measures. Under the default layout { quality: error } a residual overflow refuses the render; the variant declares quality: warn, so it renders with the text clipped at the box edge and a visible ellipsis — never invisible text. size: content artboards grow with the post-fit bounds, so wrap/grow results are always fully visible — and --content-size forces that for one render without editing the source.
**Gather first:** The text and how much it may vary; The bounds (max_width, max_height, min_font); The quality policy for overflow

**Pitfalls:** Do not set max_height without reading DDN-LW07 as a design signal — split the content or raise the bound; clipping is a last resort, not a layout style. Do not rely on estimated metrics for filings: font_pin records the measurement environment so the same source renders byte-identically anywhere (the 0.7.0 CLI cannot load pin files yet — pins apply through the host API).
**Limits:** Bounds are 40–4000 px and min_font 6–64 px (never above the base font); violations are DDN-TF02/TF03. Text fit changes geometry only — model fingerprints, endpoints and relation identities are unchanged.

## Markings and metadata — forbidden, tentative, provenance

*Techniques · technique · `field-guide/sources/markings.ddn` # `main` · ddn@1*

**What:** Model-level claims: marks: [forbidden] strikes a prohibited path, marks: [tentative] dashes uncommitted content, and assertions plus source:/generator: provenance travel with the model as authored claims.
**Why:** "This path must not exist" and "this box is a draft" are design facts; keeping them in the model means they export, diff and render under every theme — instead of living in someone's slide notes.
**When:** Migration plans (forbidden legacy paths), drafts under review (tentative scope), machine-generated documents (generator provenance), and audit claims (assertions).

**Read it:** The forbidden relation is struck and barred — under mono_print the treatment is hatch and dash, never colour alone, so the signal survives any theme. The tentative export renders dashed-grey; both markings are model facts and appear in the model fingerprint. The assertion strings and the view's source:/generator: are carried into exports and shown in tooling — in 0.8 they evaluate nothing. An unknown marking is DDN-MK01 and a duplicate is DDN-MK02; markings compose, so one element may carry several.
**Gather first:** The prohibited or draft content; The claims worth recording; The upstream document or producing tool, if any

**Pitfalls:** Do not read a passing check as proof of an assertion — assertions are inert text in 0.8; a true-looking one is not evidence and a failing-looking one is not a diagnostic. Do not mark a path forbidden and leave it routed as the only path — the marking claims prohibition, it does not remove the dependency.
**Limits:** 0.8 registers exactly two markings (forbidden, tentative); provenance is excluded from the model fingerprint and validated never. Evaluation semantics for assertions are deferred to 0.9, as are diff views.
