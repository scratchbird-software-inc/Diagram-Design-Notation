Source versions — the 0.6 dialect and when to upgrade

field-guide/sources/version-06.ddn # main

technique

What this diagram shows

The first line of every .ddn file declares its source dialect. ddn "0.6" is the 0.8 dialect: it admits view kinds, publication chrome, text fit, markings, provenance and ref: anchors.

Why use it?

The version line is a promise, not a negotiation: a 0.5 file keeps 0.5 semantics forever, and a processor never rewrites the header. Upgrading is a deliberate, per-file decision.

When is it useful?

Stamp ddn "0.6"; when the file itself needs to spell a 0.8 construct. A mixed workspace is normal — each file keeps its own declared version.

How to read this example

  1. This file declares 0.6 but uses no 0.8 construct: it renders byte-identically to the same file stamped 0.5 — only the version line differs.
  2. Using an 0.8 keyword in a 0.5-or-older file fails DDN-V04, naming the construct and the minimum version; nothing is silently accepted.
  3. The 0.8.0 runtime implements the 0.8 draft constructs, so a 0.6 file checks and renders today.

Information to gather first

  • The constructs the file actually needs
  • Who consumes the file (older tooling reads 0.5)

Boundaries and common mistakes

Accepted headers are 0.2 through 0.6; anything else (including "0.7", "0.8" or a missing line) is a parse error. Deprecated spellings keep working with an info diagnostic (DDN-V05).

  • Do not re-stamp a file "just in case" — upgrade when a construct demands it, so consumers know what they must parse.
  • Do not expect bundling or normalization to rewrite headers; they never do.
