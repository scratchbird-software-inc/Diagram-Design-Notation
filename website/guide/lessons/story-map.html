What this diagram shows

A story map: user activities across the top, stories beneath, releases sliced horizontally.

Why use it?

It keeps the walking skeleton visible while the backlog grows.

When is it useful?

Release planning for a user-facing product.

How to read this example

  1. Top row is the user's day; below is what we build, sliced by release.
  2. A story above the release line ships; below it waits.

Information to gather first

  • The activities
  • The stories under each
  • The release slices

How to author this view

  1. Open website/examples/basics/36-story-map.ddn and locate view storymap. This selects existing data; it is not a stored SVG.
  2. Inspect the matrix.storymap@1 profile and matrix projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.
Actual view declaration
view storymap "Shop rebuild / story map" {
    data: [@shop];
    format: @shared.styles.technical;
    projection { kind:matrix; profile:"matrix.storymap@1"; rows:[@shop.r1, @shop.r2]; columns:[@shop.browse, @shop.configure, @shop.checkout, @shop.pay, @shop.fulfil]; relation:"assoc"; value:"x_story.task"; duplicates:join; }
}

Boundaries and common mistakes

Declared map content; no estimation or velocity is computed.

  • Do not slice releases by component — slice by user outcome.
  • Do not let the top row become a feature list.
