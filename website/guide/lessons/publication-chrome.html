technique

What this diagram shows

Page furniture declared in the publication block: three-slot header and footer runs with $ variables, a page border, a background, and a publication_set that numbers several views as one ordered figure pack.

Why use it?

Titles, dates, page numbers and figure numbers belong in the source, not in a post-processing step — one declaration keeps every exported page consistent and reviewable.

When is it useful?

Print packs, release documentation, filings — anything that leaves the screen as a set of numbered pages.

How to read this example

  1. Runs resolve $title, $date, $view_id, $figure and $page per emitted page (a literal dollar is $$); an unknown $name fails DDN-PB02.
  2. The set's figures are numbered in declaration order — $figure and $page are their 1-based positions; publish emits one SVG per figure plus a manifest JSON.
  3. The border and background paint behind the drawing and never move it: chrome changes no model fact, no layout, no route.
  4. Pin the wall-clock variables for reproducible output: --publication-date fixes $date, and conformance vectors always pin it.

Information to gather first

  • The publication block (size, margins, minimum text)
  • The chrome text and which variables it needs
  • The ordered figure list for the set

Boundaries and common mistakes

Chrome bands reserve space outside the drawing and never overlap it; a publication declaring no chrome renders exactly as before. Print-size lint (DDN-PS01–PS03) runs at check on physical sizes only, and --strict-print promotes it to a gate (DDN-PS04).

  • Do not hand-maintain titles or page numbers in exported files — declare them once and let each page resolve its own variables.
  • Background images and patterns must live inside the workspace (PNG/WebP images, sanitized SVG patterns); absolute paths and URLs are rejected (DDN-PB05).
