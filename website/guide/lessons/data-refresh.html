Data refresh — swapping records without breaking the view

website/examples/basics/59-data-refresh.ddn # latency_chart

technique

What this diagram shows

A chart whose data block is swapped wholesale — new records, same keys, same bindings — plus the dependency graph reading of the same model.

Why use it?

Refreshes are the normal case, not the exception: a view that breaks on new data was wired to the data, not the contract.

When is it useful?

Operational dashboards, periodic re-publication, any view fed by a changing extract.

How to read this example

  1. The chart re-renders from the swapped records; bindings follow keys, not positions.
  2. The variant shows the model behind the refresh — the dependency graph does not change when only values do.

Information to gather first

  • The data block with stable keys
  • The projection bindings
  • The refresh payload

How to author this view

  1. Open website/examples/basics/59-data-refresh.ddn and locate view latency_chart. This selects existing data; it is not a stored SVG.
  2. Inspect the chart.basic@1 profile and chart projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.
Actual view declaration
view latency_chart "Latency / chart" {
    data: [@metrics];

    publication { size: content; fit: none; }
}

Boundaries and common mistakes

Record-swap refresh through the declared block; streaming or incremental updates are a host concern.

  • Do not change the key space in a refresh without migrating the bindings.
  • A refresh that changes shape (fields, not values) is a schema change — version it.
