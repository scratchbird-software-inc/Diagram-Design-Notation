technique

What this diagram shows

Model-level claims: marks: [forbidden] strikes a prohibited path, marks: [tentative] dashes uncommitted content, and assertions plus source:/generator: provenance travel with the model as authored claims.

Why use it?

"This path must not exist" and "this box is a draft" are design facts; keeping them in the model means they export, diff and render under every theme — instead of living in someone's slide notes.

When is it useful?

Migration plans (forbidden legacy paths), drafts under review (tentative scope), machine-generated documents (generator provenance), and audit claims (assertions).

How to read this example

  1. The forbidden relation is struck and barred — under mono_print the treatment is hatch and dash, never colour alone, so the signal survives any theme.
  2. The tentative export renders dashed-grey; both markings are model facts and appear in the model fingerprint.
  3. The assertion strings and the view's source:/generator: are carried into exports and shown in tooling — in 0.8 they evaluate nothing.
  4. An unknown marking is DDN-MK01 and a duplicate is DDN-MK02; markings compose, so one element may carry several.

Information to gather first

  • The prohibited or draft content
  • The claims worth recording
  • The upstream document or producing tool, if any

How to author this view

  1. Open field-guide/sources/markings.ddn and locate view main. This selects existing data; it is not a stored SVG.
  2. Inspect the ddn@1 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

0.8 registers exactly two markings (forbidden, tentative); provenance is excluded from the model fingerprint and validated never. Evaluation semantics for assertions are deferred to 0.9, as are diff views.

  • Do not read a passing check as proof of an assertion — assertions are inert text in 0.8; a true-looking one is not evidence and a failing-looking one is not a diagnostic.
  • Do not mark a path forbidden and leave it routed as the only path — the marking claims prohibition, it does not remove the dependency.
