Per-element sizing and opacity — overrides that compose

field-guide/sources/sizing-opacity.ddn # main

technique

What this diagram shows

The view-level sizing keys (text_fit, max_width, max_height, min_font) resolve per key on every element — element beats view beats engine default — plus a per-element opacity that fades a whole node.

Why use it?

One long label should not force a diagram-wide bound: declare the default once in style { } and let the noisy element counter-declare exactly the key it needs, inheriting the rest.

When is it useful?

A single oversized note in an otherwise uniform diagram, a draft node that should recede visually, a tight caption with its own shrink floor.

How to read this example

  1. summary wraps at its own 200px while the view-wide default is 320px — the element key wins, the inherited wrap mode still applies.
  2. verdict shrinks toward its own 11px floor (DDN-LW08 names the floor if the text cannot fit); the view-wide min_font of 10px does not lower it.
  3. draft paints at 0.55 opacity — fill, stroke and text fade together as one group; its box, the routing and every diagnostic are exactly as if it were solid.
  4. content_scale and DDN071 compose after the fit: the publication layer scales the post-fit drawing and checks effective sizes at the final page scale.

Information to gather first

  • The view-wide sizing default
  • The elements that genuinely deviate
  • Which nodes should visually recede

Boundaries and common mistakes

opacity is 0–1 (DDN-SZ01) and 1 is the default. Sizing bounds stay the chapter-54 ranges (DDN-TF02/TF03). Below ddn "0.6" opacity is DDN-V04; sizing keys are chapter-54 syntax with the same gate.

  • Do not re-declare the whole sizing record on an element to change one key — resolution is per key, so declare only the override.
  • Do not use opacity to hide content — it is paint-only; hit-testing, measurement and diagnostics all still see the node.
