technique

What this diagram shows

Records addressed by stable keys (refresh-safe), and the one-line view-header form that expands to a canonical declaration.

Why use it?

Keys make data refreshes order-independent; the compact header makes small views writable without boilerplate.

When is it useful?

Data-bound views that refresh, and any view small enough to say in one line.

How to read this example

  1. The chart binds records by key — reordered or refreshed data lands on the same bars.
  2. The variant shows the compact form: one header line desugars to the same data + projection the verbose form declares.

Information to gather first

  • The records with their keys
  • The projection binding
  • The compact header form for small views

How to author this view

  1. Open website/examples/basics/12-nested-fields.ddn and locate view metrics_chart. This selects existing data; it is not a stored SVG.
  2. Inspect the chart.basic@1 profile and chart projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.
Actual view declaration
view metrics_chart "Order timings / keyed tabular records" {
 data: [@metrics];
 projection { kind: chart; profile: "chart.basic@1"; records: [@metrics.m1, @metrics.m2, @metrics.m3, @metrics.m4]; mark: bar; x: "x_record.label"; y: "x_record.value"; unit: "ms"; width: 900px; height: 560px; }
 publication {size: content;fit: none;}
}

Boundaries and common mistakes

Keyed binding and header desugaring as specified; no schema inference beyond the declared records.

  • Do not rely on record order once keys exist — keys are the contract.
  • The compact form expands to canonical declarations; if you need more, write the verbose form.
