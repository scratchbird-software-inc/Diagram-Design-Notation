What this diagram shows

Decisions, input data and knowledge sources as nodes; information-requirement arrows saying what each decision needs.

Why use it?

The DRD is the table of contents for the decision logic — reviewers can demand to see every input's source.

When is it useful?

Before writing the decision tables: agree what is decided from what.

How to read this example

  1. Rectangles are decisions, ovals are input data; arrows point from requirement to the decision that requires it.
  2. Variants open the actual decision tables behind two of the decisions.

Information to gather first

  • The decisions
  • The input data
  • The authority (knowledge sources)

How to author this view

  1. Open website/examples/basics/87-dmn-drd.ddn and locate view drd. This selects existing data; it is not a stored SVG.
  2. Inspect the dmn.drd@1 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

Declared requirements graph with reference validation; the tables' logic is validated separately (see the decision-table chapters).

  • Do not let a decision read data that never enters the diagram.
  • A decision nobody requires is dead logic — delete it or wire its consumer.
