What this diagram shows

Fields nested inside elements: domains and physical representations as collapsible rows, with identities that survive the collapse.

Why use it?

Logical-to-physical detail belongs on the element, and collapsing must never lose the endpoint a relation lands on.

When is it useful?

Domain modelling where each attribute carries a type, a domain and a physical representation.

How to read this example

  1. Rows inside an element are its nested fields; indentation is the nesting.
  2. The collapsed variant hides rows — relation endpoints still resolve to the same identities.

Information to gather first

  • The elements
  • The nested field rows
  • The relations into nested endpoints

Boundaries and common mistakes

Declared nesting with identity preservation validated across collapse; type checking beyond declaration is out of scope.

  • Do not model a field as a separate box when it belongs to its element.
  • Collapsing is a view choice — if an endpoint vanishes, that is a defect, not a feature.
