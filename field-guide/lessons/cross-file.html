What this diagram shows

A strategic-capabilities view whose model is split across files — traces resolve across file boundaries into one render.

Why use it?

Real architectures outgrow one file; the trace view proves references stay intact when the model is partitioned.

When is it useful?

Multi-file models: governance in one file, operations in another, one view over both.

How to read this example

  1. The boxes and traces read exactly as a single-file view; the file boundary is invisible in the render.
  2. Imports in the source declare which file supplies which elements.

Information to gather first

  • The partitioned model files
  • The import declarations
  • The trace relations

How to author this view

  1. Open website/examples/basics/108-uaf-traceability.ddn and locate view sv. This selects existing data; it is not a stored SVG.
  2. Inspect the uaf.strategic@1 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

Cross-file references resolved at render time; no external repository or versioning semantics are implied.

  • Do not duplicate an element id across files "for convenience" — import it.
  • A broken import fails the render; check diagnostics before assuming the trace is wrong.
