What this diagram shows

Actions wired by object and control flow: pins as typed ports on actions, decision/merge diamonds, fork/join bars, interruptible regions.

Why use it?

The activity diagram is where "the process" becomes checkable: every input must come from somewhere.

When is it useful?

Detailing an algorithm or business process one level below a use case.

How to read this example

  1. Rounded boxes are actions; small squares on their edges are pins (typed inputs/outputs).
  2. Diamonds decide or merge; thick bars fork and rejoin concurrent flow.

Information to gather first

  • The actions
  • What each consumes and produces
  • The decision logic

How to author this view

  1. Open website/examples/basics/80-uml-activity.ddn and locate view pins. This selects existing data; it is not a stored SVG.
  2. Inspect the uml.activity@2 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

Declared flow with pin and region validation; no execution or simulation is performed.

  • Do not leave a required pin unfed — the validator treats it as the defect it is.
  • Merge and decision are different diamonds; do not swap them.
