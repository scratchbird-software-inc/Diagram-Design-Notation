What this diagram shows

A preliminary map of named concepts and their relationships. An unspecified object deliberately leaves storage technology and detailed structure undecided; it is not an undocumented SQL table.

Why use it?

Use this to expose disagreements about vocabulary before implementation choices obscure them. A shared sketch provides stable identities that can acquire fields, domains and deployment details later.

When is it useful?

Start an unfamiliar project or facilitate a meeting where participants need to agree on the important things before they agree on keys and types.

How to read this example

  1. Read the nouns in the boxes first.
  2. Read each connecting verb as an assertion, not as an enforced foreign key.
  3. An unselected element is out of scope for this sketch, not deleted from the model.

Information to gather first

  • Names understood by the participants
  • Relationship meanings and direction
  • Questions that have not been settled

How to author this view

  1. Open website/examples/use-cases/01-whiteboard.ddn and locate view diagram. This selects existing data; it is not a stored SVG.
  2. Inspect the ddn@1 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

This is an explanatory model, not an executed business system. A successful render does not establish implementation effectiveness or independent approval.

  • Do not infer a table from every rectangle.
  • Do not treat proximity, colour, or a crossed line as a new fact.
