What this diagram shows

Packages grouping model elements with imports and merges, and profiles declaring stereotypes that extend the metamodel.

Why use it?

Large models fail at the boundaries between teams; packages declare those boundaries and who depends on them.

When is it useful?

Partitioning a big model, or documenting a domain-specific UML extension.

How to read this example

  1. A folder shape is a package; dashed arrows are imports/merges with direction.
  2. In the profile variant, stereotypes and tagged values extend, never replace, the base metaclass.

Information to gather first

  • The packages and their members
  • The import/merge relationships
  • Stereotypes for the profile

How to author this view

  1. Open website/examples/basics/81-uml-remainder.ddn and locate view packages. This selects existing data; it is not a stored SVG.
  2. Inspect the uml.structure@2 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

Declared packaging and profiling; element ownership is validated, code packaging is not implied.

  • Do not let imports form a cycle — that is one package wearing two hats.
  • A stereotype without a base metaclass is undefined.
