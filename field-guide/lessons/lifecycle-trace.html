What this diagram shows

A flat lifecycle diagram plus its trace checker: replay a declared event list through the states and verify the outcome.

Why use it?

The state machine you cannot run an event list through is a picture, not a contract.

When is it useful?

Checking that a declared lifecycle actually reaches the states its name implies.

How to read this example

  1. States and transitions are the model; the trace is a recorded input you replay.
  2. A mismatch names the event and the expected state.

Information to gather first

  • The states and transitions
  • The event list to replay
  • The expected end state

How to author this view

  1. Open website/examples/quality/views.ddn and locate view lifecycle_trace. This selects existing data; it is not a stored SVG.
  2. Inspect the state.flat@1 profile and graph projection. Read the bindings before changing any value.
  3. Use the source-file picker or select a diagram element to find its declaration. Edit labels or values deliberately; keep identifiers stable unless all references are updated.
  4. Apply the source, inspect diagnostics, and compare the expected result. Export the SVG only after a successful render.

Boundaries and common mistakes

Deterministic flat-lifecycle replay with exactly-one-transition validation.

  • Do not treat a passing trace as proof of all traces.
  • Do not hide an event the machine cannot consume.
