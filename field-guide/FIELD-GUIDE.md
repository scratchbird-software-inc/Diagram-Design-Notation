## Logical relational schema

*Data structures and meaning · native · `website/examples/use-cases/03-relational.ddn` # `diagram` · ddn@1*

**What:** Tables and references at design level: keys, cardinalities and which table owns a fact — still no storage engine decisions.
**Why:** Move from business nouns to a checkable structure: every relationship now has a home and a direction.
**When:** After the conceptual ER pass, before physical naming, indexing and platform choices.

**Read it:** Each box is a table; read keys first, then the reference arrows from foreign key to primary key. Crow's-foot marks state how many children a parent may have — claims, not constraints enforced here.
**Gather first:** The entity list from the conceptual model; Candidate keys per table; Ownership rules for every relationship

**Pitfalls:** Do not put a foreign key on both sides. A many-to-many without a join table hides a missing entity.
**Limits:** Logical only: datatypes, indexes and platform types are declared in the physical model, not here.

**Guided first edit:** Only the label of Customer / review changes; keys, references and every identity are untouched. (evidence: render changes, undo restores shipped bytes: true)

## Physical representation and datatype documentation

*Data structures and meaning · native · `website/examples/use-cases/04-sql-dependencies.ddn` # `diagram` · ddn@1*

**What:** SQL objects with their dependencies: which view reads which table, which table feeds which report.
**Why:** Know the blast radius of a schema change before you make it.
**When:** Impact analysis before renaming, splitting or dropping database objects.

**Read it:** Arrows point from a definition to the objects that consume it. A shared lookup table with many consumers is a deliberate coupling, not an accident.

**Limits:** Declared dependencies only; runtime introspection of a live database is out of scope.

## Document and embedded-object schema

*Data structures and meaning · native · `website/examples/use-cases/05-documents.ddn` # `diagram` · ddn@1*

**What:** A document model: nested objects, arrays and embedded structures with their containment rules.
**Why:** Tree-shaped data needs its own contract — tables of one row type do not describe nesting.
**When:** Designing JSON documents, message payloads, or any hierarchical record.

**Read it:** Containment reads top-down: each level owns the fields below it. Arrays are plural by contract, not by current length.
**Gather first:** The nesting levels; Which fields are arrays; Required-versus-optional per node

**Pitfalls:** Do not flatten a tree into parallel tables just because it feels relational. An optional node with required children is usually a modeling mistake.
**Limits:** Structural contract only; no validation engine runs against live documents.

## Key-value structure and lookup contract

## Wide-column and access-pattern design

## Semantic domains and candidate bindings

*Data structures and meaning · native · `website/examples/use-cases/08-domains.ddn` # `diagram` · ddn@1*

**What:** Semantic domains: named value sets with their rules, and which fields bind to which domain.
**Why:** Shared meaning beats shared spelling — a domain contract stops "status" meaning six different things.

**What:** Marks plus statistics: error bars on declared uncertainty, regression and loess lines fitted to the records.
**Why:** The overlay separates the measured fact from the fitted model — and says which is which.
**When:** Reporting measurements with uncertainty or trend models.

**Read it:** Points are records; the line is a model of them, named with its method. Error bars are declared ranges, not computed guesses — unless the view declares the computation.
**Gather first:** The records; The uncertainty per point (if any); The fit method

**Pitfalls:** Do not show a fit without naming its method. Do not let the line outrun the points it claims to summarise.
**Limits:** Declared fits from declared data; no confidence interval is invented.

**Guided first edit:** Only one point changes; fits, ranges and identities are untouched. (evidence: render changes, undo restores shipped bytes: true)

## Whiteboard / discovery sketch

*Data structures and meaning · native · `website/examples/use-cases/01-whiteboard.ddn` # `diagram` · ddn@1*

**What:** A preliminary map of named concepts and their relationships. An unspecified object deliberately leaves storage technology and detailed structure undecided; it is not an undocumented SQL table.
**Why:** Use this to expose disagreements about vocabulary before implementation choices obscure them. A shared sketch provides stable identities that can acquire fields, domains and deployment details later.
**When:** Start an unfamiliar project or facilitate a meeting where participants need to agree on the important things before they agree on keys and types.

**Read it:** Read the nouns in the boxes first. Read each connecting verb as an assertion, not as an enforced foreign key. An unselected element is out of scope for this sketch, not deleted from the model.
**Gather first:** Names understood by the participants; Relationship meanings and direction; Questions that have not been settled

**Pitfalls:** Do not infer a table from every rectangle. Do not treat proximity, colour, or a crossed line as a new fact.
**Limits:** This is an explanatory model, not an executed business system. A successful render does not establish implementation effectiveness or independent approval.

**Guided first edit:** Only the label of Customer / review changes; identities, relations and every other declaration are untouched. (evidence: render changes, undo restores shipped bytes: true)

## Conceptual business ER diagram

**What:** Entities and the relationships between them at business level: names and cardinalities, no storage design.
**Why:** Agree on the things the business tracks before any schema discussion; the diagram is the vocabulary contract.
**When:** Early domain workshops and any review where business stakeholders must confirm scope without reading SQL.

**Read it:** Entities are nouns; relationships are verbs with cardinality marks. Participation marks (zero/one/many) are claims about the domain, not constraints enforced here.

**Limits:** Conceptual only: no keys, types or indexes are decided by this view.

## IEC 61131-3 ladder diagram / relay logic

*Processes, interactions and lifecycle · native · `website/examples/basics/101-ladder.ddn` # `d` · ladder.basic@1*

**What:** Three rungs between the power rails: normally-open and normally-closed contacts driving coils, one coil per rung, a parallel OR branch, and a hosted function block.
**Why:** Ladder logic is the control-room reading of combinatorial logic: conditions left-to-right, one output per rung.
**When:** Industrial control documentation where electricians and engineers share one reading of the wiring.

**Read it:** Power flows conceptually left rail to right rail. Contacts in series are AND; contacts stacked on parallel tracks are OR. One rung drives exactly one coil — the validator enforces it.
**Gather first:** The signals (contacts); The outputs (coils and their modes); Rung order

**Pitfalls:** A rung with two coils is an error, not a design. Branches come from the wiring topology — you do not declare them.
**Limits:** Common-practice ladder rendering and validation; no PLC compilation, execution or IEC XML interchange.

**Guided first edit:** Only the label of START / review changes; rungs, contacts and the coil are untouched. (evidence: render changes, undo restores shipped bytes: true)

## Typed decision table — first match

*Matrices, tables and analysis panels · native · `website/examples/quality/views.ddn` # `decision_first` · decision.rules@1*

**What:** A typed decision table evaluated in first-match order: the first row whose conditions all match produces the outcome.
**Why:** Expose rule order as a deliberate design decision instead of an accident of presentation.
**When:** Bounded business rules where precedence must be reviewable line by line.

**Read it:** Read rows top-down: the first fully-matching row wins. Type domains on each input gate what a row may claim.
**Gather first:** The input fields and their domains; The rule rows in priority order; The output column

**Pitfalls:** Row order is normative here — reordering rows changes outcomes. A gap in the domain is a silent fall-through, not a default row.
**Limits:** Bounded decision-table evaluation against one input record; no arbitrary rule-language execution.

**Guided first edit:** Only the label of High severity / review changes; rules, domains and the evaluation contract are untouched. (evidence: render changes, undo restores shipped bytes: true)
